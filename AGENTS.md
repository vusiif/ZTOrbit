# Project maintenance

- Code/project names remain `ZTOrbit` (`zto`) and `ZTOrbitHub` (`ztohub`); distributed artifacts use `Z2` / `Z2Hub`, file prefixes `z2_` / `z2hub_`, and client package extensions `.z2plugin` / `.z2bundle`. The client window title is `Z2`. Keep internal build targets, namespaces, Maven coordinates, macros, IDs and protocols in zto/ztohub. Use `vusiif::zto` for client/shared C++, `vusiif.ztohub` for Java server packages and Maven group IDs, and `vusiif::ztohub` for archived C++ server code. Use `ZTO_` / `ZTOHUB_` macro prefixes. See `docs/naming.md` for SDK names and intentional historical references.
- Keep the public plugin SDK under `src/client/api/`, application implementation under `src/client/main/`, plugin projects under `src/plugins/<plugin>/client/`, and tests under `src/tests/`. The API must not depend on host implementation headers or sources. Respect an explicitly requested alternative plugin directory.
- The Linux server follows the same separation under `src/server/api/` and `src/server/main/`, with Java plugins under `src/plugins/<plugin>/server/`. The server is a Java 25 + Netty + Maven application; the archived C++/Qt6 implementation, its tests and its C++ voice plugin live in `src/server-old/` and are added by the root CMake only with `ZTO_BUILD_SERVER_OLD=ON` (the archived directory also keeps its own CMake and script entry points). Shared client/legacy wire protocol lives under `src/shared/include/`; plugin-specific shared code lives under `src/plugins/<plugin>/shared/` — the voice protocol there is shared by the client and the archived C++ server, and the Java server re-implements it byte-compatibly. Versions are split: the client application and client API derive from root `VERSION`; the server application and server API derive from root `SERVER_VERSION`, which the client side owns and the server build reads. Client and server releases are independent. Client plugins use `.z2plugin` packages with IIDs, while Java server plugins use JAR manifests with `apiVersion`.
- The developer manages the version files: `VERSION` (client) and `SERVER_VERSION` (server, specified by the client side). Do not edit either for functionality, build, documentation, fixes, or optimizations; change them only when explicitly instructed by the developer. Record pending changes in an unreleased `CHANGELOG.md` section when no new version has been assigned.
- Before the first official release, use application versions `0.<core>.<patch>[-qualifier]` and API versions `0.<core>[-qualifier]`. The API qualifier must equal its application qualifier. The major version stays 0; the current client core/API generation is 5 (client `0.5.3`, API `0.5`) and the server generation is 2 (server `0.2.2`, API `0.2`). When the developer assigns a non-core update version, change only the patch; when assigning a core/API generation change, update the middle number and reset the patch to 0. Use the qualifier the developer assigns, and keep the API qualifier equal to the application qualifier on that side. Never change the major version or a core generation without an explicit user request.
- Each side's version file is the single source of truth: `VERSION` for the client application, About dialog, Windows file metadata, and macOS bundle versions; `SERVER_VERSION` for the server application, `--version`, package metadata, and server API. Do not hard-code separate version values in source code.
- Derive client API constants and SDK package metadata from the first two numeric components of `VERSION` plus its qualifier; derive server API values from `SERVER_VERSION` the same way. Pre-release plugins must match the full API version exactly; application patch changes do not change plugin compatibility.
- The application is still before its first official release, so breaking changes and architectural refactors are expected and tolerated. Prefer a clean design over backward compatibility: do not add legacy aliases, compatibility shims, or deprecated entry points. When a change breaks the plugin API or ABI, recompile the affected plugins and SDK consumers, update the docs, and record the migration under the unreleased changelog. Version and API-generation changes still follow the rules above; do not edit `VERSION` or `SERVER_VERSION` on your own.
- The developer explicitly assigned client `0.5.3` (API `0.5`) and server `0.2.2` (API `0.2`) for the current release; the client side specifies the server version in `SERVER_VERSION`. Record future unassigned changes under the unreleased changelog section; see the version rules in `docs/maintenance.md`. The repository currently retains only `main`; do not recreate the retired `dev-net` or `codex/restore-ui-functions` branches without a developer request.

# Plugin development skill

When creating, modifying, or independently compiling a plugin, read [zto-plugin-dev](.agents/skills/zto-plugin-dev/SKILL.md). This project skill covers directory creation, public API dependencies, implementation, and compilation.

# Build and packaging skill

For application builds and release packaging, read [zto-build](.agents/skills/zto-build/SKILL.md). Build and compress the main application and the Java Linux server; update and compress the public API SDK only when its inputs or package changed. Build plugins when the user requests them or their own plugin version changes; a version change requires recompiling and repackaging the corresponding plugin. Keep generated CMake trees, toolchain dependencies and release artifacts under `build/` (`build/cmake-build-*`, `build/dist/`); the repository root must stay free of `cmake-build-*` and `dist/`. Delete obsolete build backups such as `.previous-*` after successful validation; do not retain build backups. Packaging implementation lives in the build skill's `scripts/` directory.

# Documentation

Keep README concise: architecture, structure, platforms, building, and plugin development. Preserve non-obvious deployment assumptions and design constraints in `docs/`. Do not retain dated validation archives, raw test output, screenshots, or artifact hashes there; report validation results in the task delivery notes. Do not archive removed UI usage instructions or facts readily discoverable from source. See [maintenance notes](docs/maintenance.md).

Network deployment and default connection behavior must follow [network conventions](docs/network-conventions.md), the single source for server/ID association, ports, IPv4 /24 networks, and the server's fixed .1 address. Deployments outside these conventions are unsupported and are the deployer's responsibility; do not infer support from configurable command arguments or test overrides. Update the conventions explicitly before changing these defaults or broadening supported deployments.

Plugin documentation is owned by each plugin project and lives under `src/plugins/<plugin>/client/docs/` or `src/plugins/<plugin>/server/docs/`. Root documentation may link to it, but should not maintain a separate copy. Application icons and resource templates live under `src/client/assets/`.
