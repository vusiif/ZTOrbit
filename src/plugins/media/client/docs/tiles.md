# 自适应桌面分块：bgra-tiles

面向文字、代码和静态界面，保持 BGRA 像素无损；H.264 保留用于视频等持续运动内容。不承诺分块在所有内容上都比 H.264 省流量，也不把局部更新次数称为完整画面帧率。

## SDK

通过 `capabilities().compiled.video` 检查 `bgra-tiles`，设置 `TrackConfig.codec.codec="bgra-tiles"`、`video.colorRange="full"`。最大尺寸 1920×1080，宽高须为偶数，帧率范围 1–60；桌面共享当前提供 720p30／2 Mbps、1080p30／4 Mbps 两档。初始化数据必须为空；硬件编码、处理器链、音视频同步组请求会被明确拒绝。

仍通过 `MediaSession::packet`、`submitTo()` 和完整 BGRA `FrameView` 使用，不要求业务插件解析块或链接 worker 实现。预览像素为 full range；画布就绪后立即显示，不进入 H.264／音频播放时间线。

`MediaSession::keyFrameRequired(receiveTrackId)` 回调表示需要发送者提供新基准。应用映射到对应发送轨道：本地回环调用 `requestKeyFrame()`，网络观看经控制协议转发。worker 对每个接收轨道每秒最多通知一次。

`requestKeyFrame()` 对 H.264 请求 IDR，对分块请求新一代完整基准；有有效采集画布时可用缓存响应静态来源，没有任何采集帧时仍须等待来源。刷新另计 `keyFrameRefreshes`，不增加 `captured`，不作为来源仍有效或对端已收到的证明。`Statistics::track(id)` 返回拥有所有权的轨道 JSON 快照，未知 ID 返回空对象。

## 发送策略

1. 来源先合成固定尺寸、保持原始比例的黑色画布，再分成 64×64 块；边缘块允许不足 64。
2. 首次或刷新时冻结基准快照并优先发送全部块。接收端所有位置至少到达一次才显示，不用重复区域填充未知位置。
3. 后续逐行比较最新采集与已发送画布，只发送实际变化的块，不用哈希碰撞概率代替像素判定。
4. 待发送块使用循环游标，预算不足时从剩余块继续；等待期间保留最新采集，不堆积历史帧或让热点区域占住发送机会。
5. 编码包频率不超过配置帧率；令牌桶按完整编码负载计字节，突发容量为 `clamp(码率字节/秒 ÷ 4, 32768, 262144)`，刷新和同轨停止／重启不重置令牌。
6. 没有变化或待发块时，每 500ms 最多发送一个 40 字节状态包，不产生新预览，用于发现最后一个更新包丢失。
7. 编码器以 8 KiB 为单包突发目标；一个不可压缩块允许单独占用 16,432 字节（16 KiB 像素＋记录与包头），避免小包目标永久饿死该块。完整基准跨多个包，基准标记表示本包包含基准块，不能当作本包已包含完整首屏。桌面共享网络接收按绝对块语义保留乱序基准包，不采用 H.264 的跨包依赖策略。
8. 变化块发送截止时间从上一截止时间推进，不反复重置为 `now + 帧间隔`。多个观看者重复请求关键帧时，已开始的基准不重启；在途请求合并为一个后续完整基准，当前基准结束后才开始，不丢弃晚就绪接收者的请求。`tileRefreshPending` 记录该有界请求槽。

H.264 发送按配置帧率累积令牌、上限 2 个令牌：亚帧率来源直通，超帧率来源长期不超过配置值。桌面共享默认编码为 H.264（帧率优先、约 2 Mbps 质量）；变化块保留为可选无损模式。

这里的预算不包含 UDP、ZTS1 和 IP 开销；网络业务层仍须按完整报文限速。照片、噪声和全屏运动可能采用原始块并降低区域刷新速度，适合改用 H.264。不能把配置的 30fps 或支持 60fps 参数当作实测性能结论。

预算下各区域可能来自不同采集时刻。全屏变色或连续运动时可见条带或不同区域更新不同步，这是局部轮换的时间取舍；需要整帧运动一致性时选择 H.264。无损只表示已接收块的像素精确，不表示每个区域都保持配置帧率。

## ZTD1 负载

大端序，固定 40 字节头，单个编码包最多 256 KiB。负载保持原样经过网络分片；媒体 SDK、编码内部和网络传输的包序号可以不同。

| 偏移 | 字段 | 字节／约束 |
| --- | --- | --- |
| 0 | magic | 4，`ZTD1` |
| 4 | version | 1，固定 1 |
| 5 | flags | 1，bit0=完整基准块，bit1=状态包，互斥，其余为零 |
| 6 | tileEdge | 2，固定 64 |
| 8 | width | 2，与接收轨道一致 |
| 10 | height | 2，与接收轨道一致 |
| 12 | recordCount | 2，状态包为零，其他包至少一条，最多为画布块数 |
| 14 | reserved | 2，零 |
| 16 | baselineEpoch | 8，非零，完整刷新递增 |
| 24 | epochStartSequence | 8，本代首个编码包的内部序号 |
| 32 | codecSequence | 8，内部单调序号，包括状态包 |

块记录为 `tileIndex:u16`、`encoding:u16`、`payloadBytes:u32` 和对应负载。块按行编号，同一包不能重复编号；块尺寸由位置及画布计算。

- `encoding=0`：紧凑逐行 BGRA，长度恰好为块宽×块高×4。
- `encoding=1`：像素 PackBits。token 低七位加一表示 1–128 个像素；最高位为 1 时后接四字节 BGRA 并重复该次数，为 0 时后接指定数量的 BGRA 像素。
- `encoding=2`：独立 zlib Deflate 流（不含 qCompress 的四字节长度前缀），输入为该块紧凑逐行 BGRA。编码器以 level 1 在原始、PackBits、Deflate 中选择最短结果。解码器直接向该块精确尺寸的固定缓冲区 inflate，要求流结束、输出恰好匹配且无尾随字节；截断、膨胀越界与额外尾部均拒绝。Qt 内置 zlib 只作为 worker 私有依赖，不进入公开 SDK。
- 压缩不小于原始数据时使用原始编码。单块编码负载最多 16,384 字节，解压严格限制为该块精确尺寸，不按远端任意长度分配或无界膨胀。

`encoding=2` 与既有编码同在 worker 内实现；旧 worker 不识别该编码，需同时更新同一媒体包。公共 Media API、服务签名、版本文件和 API 代际不变。
- 外层 `EncodedPacket.keyFrame` 与完整基准标志一致，所有基准块包均带该标志；状态包不带关键帧标志。时间戳仍由 `EncodedPacket`／网络头携带。

## 恢复和资源上限

块为绝对像素，不依赖其他块或之前的像素差；接收端按内部代次和每块最新内部序号拒绝旧更新。同一接收轨道刷新时保留已验证块及其最新内部序号，让多次不完整刷新可以补齐首屏；所有位置至少验证一次前不显示未知像素。更旧的代次不能回写；新代次起始序号不得倒退到此前已观察位置。换源／重新协商网络流建立新的接收轨道和解码器，不继承旧来源覆盖。缺包表最多 1024 项，缺口等待 200ms 后请求刷新；超出窗口直接请求，不扩大缓存。状态包暴露最后一次丢失；不完整首屏没有进展时也请求刷新，阈值随最低块发送时间增大，避免低码率正常发送被当作超时。

私有统计包含基准代次、起始与下一包序号、发送基准是否在途、已知块覆盖和缺包数；桌面共享测试按时间采样并与发送／转发片段头绑定。字段不包含像素、token 或房号。

同一发送轨道停止时释放画布与待发块，但保留内部代次、序号和预算历史；重启生成更新的完整基准，仍运行的接收轨道不会把它误判为旧代次。新建发送轨道或重新配置后的网络流须另行协商流代次，不能沿用旧流身份。

编码端最多保留最新、基准和已发送三张固定画布；单次输出最多 256 KiB。解码先校验整包，再应用记录，拒绝非法压缩、重复块、截断、尺寸不符、保留位和超限输入，不显示半包内容。最大画布为 30×17=510 块，宿主既有轨道、IPC、预览槽预算继续生效。

桌面共享 UDP 重组另外限制八个未完成编码包、合计 8 MiB、200ms 到期，以及 1024 个已完成／淘汰序号。真实 UDP 测试覆盖乱序、重复、丢片和 SDK 恢复通知。
